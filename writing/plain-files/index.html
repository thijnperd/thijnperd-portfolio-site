Plain files, no accounts

Four projects, one rule: the data belongs in a folder the person can inspect, move and back up without asking a server for permission.

Published
27 Nov 2026
Reading
7 minutes
Topics
Local-first, file formats
Projects
Four

The default is somebody else's computer

Most software now assumes an account. Notes, images, plans and research live in a service, in a format the service defines, reachable while the service is reachable. It is a good deal for synchronisation, and a bad one for everything else: the tool can disappear, the format can change, the price can move, and the data cannot be opened without the app that wrote it.

The four projects on this site point the other way. Not because the cloud is evil, but because for these particular tools the local version is simpler, faster and easier to trust. The file is the interface.

What that looks like in practice

  • Dither Studio's web build opens from its own folder with no build step and no runtime dependencies. A finished piece exports as PNG, text, WebM or a JSON recipe; the recipe is the whole setup, readable in any editor.
  • Cortex reads a vault of Markdown where it already lives. There is no import, no database and no copy. If the app is deleted, the notes are untouched.
  • W3Plan keeps a student's schedule on the device. The school's PTA data is the one thing fetched from outside, and it is read-only.
  • PapersPlease writes nothing to a service at all. It queries public APIs, links to open-access papers, and leaves the reading to you.

What it buys

It opens. No session check, no loading state, no "contact your administrator". A folder of static files is the fastest kind of app there is.

It works offline. On a train, in a basement, on a school network that blocks everything. The tool does not care, because nothing essential is remote.

The files outlive the app. Markdown, PNG, WebM and JSON are readable without this codebase. That is the real exit plan: not a data export feature, but data that never needed exporting.

Backups are boring. A folder can be copied, zipped, put in git or dropped on a USB stick. There is no restore flow to test and no account recovery to lose.

There is no permission model. No sharing settings, no roles, no link that is accidentally public. Access is whatever the filesystem says it is.

What it costs

No sync. Two machines mean two copies, and merging them is the user's problem. This is the biggest cost and the one that rules out some products entirely.

No collaboration. Two people editing the same file at the same time is a hard problem, and "put it in a shared folder" is not a solution. A tool that needs real-time collaboration needs a server; pretending otherwise just moves the conflict.

You own the backups. Local-first means the failure mode is local too. A deleted folder is gone unless the person made a copy.

Distribution is on you. Installers, updates and code signing are the unglamorous tax on desktop software. W3Plan ships auto-updating builds for Windows and macOS, and that machinery took more care than some of the features.

Local compute has a ceiling. Anything that needs a large model or a lot of CPU is harder without a server, and sometimes not worth doing locally at all.

Where the cloud earns its place

W3Plan is the useful counterexample. The school's PTA calendar is published data that every student needs and no student should edit. Fetching it read-only from Supabase — with a local JSON fallback — is better than shipping a copy that goes stale. The division is clean because the data has an owner and a direction: published by the school, consumed by the app, never written back.

That is a reasonable rule of thumb. Data a person creates stays local. Data an institution publishes can be fetched. Data two people must edit at once needs a real sync model, and the product should say so rather than pretend a folder is one.

The test

A simple question decides most of these cases: if the service disappeared tomorrow, what would the user still have? If the answer is "a folder of files that open in anything", the design is probably right. If the answer is "a login screen", it is worth asking what the account is actually buying.
